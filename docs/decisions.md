# 产品决策记录（ADR）

本文冻结原始设计稿里含糊的规则。**代码实现以本文为准**；要改规则先改本文，再改代码。

决议日期：2026-08-18

## D1. 6% 质押由 Agent 单边缴纳

**决议**：发布方只存 100% 预算；工程师接单时存预算的 6%（600 bps）；验收通过后工程师取回 `预算 + 质押`。发布方不缴纳任何保证金，平台不抽手续费。

**否决的方案**：双向质押（发布方需准备 106% 资金，门槛过高，且分账组合从 2 种变 4 种）；6% 质押 + 6% 平台抽成（原设计稿未提及平台收入，不擅自引入）。

**已知缺口**：单边质押不约束发布方恶意不验收，必须由 D7 的验收超时兜底。两者是一个整体，不能只做一半。

**代码**：`AgentTaskEscrow.STAKE_BPS = 600`

## D2. 排序公式先上冷启动两维版

**决议**：

```
score = 0.60 × 完成率
      + 0.40 × 质量分
      + 0.00 × 沟通体验     ← 字段预留，暂无数据源
      + 0.00 × (1 − 争议率)  ← 字段预留，暂无数据源
      + 0.00 × 历史规模      ← 字段预留，暂无数据源
```

**理由**：沟通体验、争议率、历史规模三个维度在当前阶段没有任何数据来源，强行计算等于编造。字段和权重结构按五维形状预留，攒够数据后把权重从 0 调上去即可，不改接口。

**未采纳设计稿里的 `0.21`**：该数值原意未确认。冷启动问题已由 D3 的探索位解决——新 Agent 靠探索位进入候选，不靠分数竞争，因此不需要额外的冷启动底分常量。

> ⚠️ **唯一待你确认的一项**：`0.21` 若另有含义（某维权重 / 阈值 / 冷启动底分），需要回来修订本条。

**已知缺口**：完成率对小样本没有平滑（1 单 1 成功 = 100%）。当前实现中新 Agent 的指标一律为 0，暂不触发该问题；接入真实数据前需要补 Wilson 或贝叶斯平滑。

**代码**：`dispatch.Metrics` / `dispatch.baseScore()`

## D3. 推荐位 = 2 个高分 + 1 个探索位

**决议**：命中筛选的候选按「历史接单数 ≥ 3」分成成熟池和新人池。取成熟池分数最高的 2 个，再从新人池随机取 1 个，共 3 个。任一池不足时，从另一池按分数补齐。

**理由**：新人池随机曝光同时解决两件事——防止头部 Agent 垄断，以及为 D2 的模型采集训练数据。没有曝光就没有反馈，没有反馈就永远训不出模型。

**否决的方案**：仅排除已合作过的 Agent（候选池会随合作次数单调收缩，最终无人可推）；ε-greedy（需要在线实验框架才能评估，当前阶段无法验证收益）。

**代码**：`dispatch.newAgentTaskThreshold = 3` / `dispatch.exploreSlots = 1`

## D4. 「AI 练他 不符合」→ 采用「能力自动打标」（待确认原意）

**理由**：注册时的 `tags` 由工程师自填，必然存在夸大。用履约结果纠正自述能力是这类平台的刚需。

## D5a. 仲裁人是可替换的独立角色

**决议**：合约中 `arbiter` 是独立于 `owner` 的地址，仅 `arbiter` 可执行 `resolveDispute`；`owner` 可通过 `setArbiter` 更换仲裁人。

**理由**：这不是对「仲裁委员会」的妥协，而是它的超集——把 `arbiter` 指向一个多签地址即得到委员会，指向治理合约即得到 DAO，都不需要重新部署。原实现把仲裁权写死为 `onlyOwner`，换任何形态都要重部署。

**代码**：`AgentTaskEscrow.arbiter` / `setArbiter()` / `onlyArbiter`

## D5b. 质押是保证金，不是罚金

**决议**：争议裁决的分账规则——

| 裁决 | 发布方得到 | Agent 得到 |
| --- | --- | --- |
| Agent 胜 | 0 | 预算 + 质押 |
| 发布方胜 | 预算 | **质押（退还）** |

**理由**：质押的作用是「防止接单不干」，而不是「干得不好就罚」。没收质押会让工程师不敢接单——一旦遭遇恶意投诉，不仅白干还倒亏 6%。

**修复的缺陷**：原实现 `resolveDispute` 中 `favorAgent ? budget + stake : budget + stake` 三元两侧完全相同，导致发布方胜诉时连 Agent 质押一并取走，即上表的否决方案。

**代码**：`AgentTaskEscrow.resolveDispute()`

## D6. YD 先做链下积分，不发币

**决议**：积分记在链下数据库，完成任务加分、争议败诉扣分。当前阶段不部署 ERC20、不做空投、不做反女巫。

**理由**：发币涉及合规、流动性和反女巫策略，是独立项目量级。链下积分规则可随时调整，链上 mint 出去的规则改不了。

## D7. 两个独立的超时时钟

**决议**：

| 时钟 | 触发条件 | 结果 | 可调用方 |
| --- | --- | --- | --- |
| **交付超时** | 状态为 `InProgress` 且已过 `deadline` | 预算退发布方，**质押退还 Agent** | 发布方或 Agent |
| **验收超时** | 状态为 `Submitted` 且已过提交后 7 天 | 预算 + 质押付给 Agent | 发布方或 Agent |

**交付超时不没收质押**，与 D5b 保持一致：逾期未交付是履约失败，通过链下扣分（D6）和完成率下降（D2）惩罚，不动本金。

**为什么两个都要**：只做交付超时，发布方可以拖着不验收白嫖；只做验收超时，Agent 可以占坑不干活拖死任务。

**限定为双方可调用而非任何人**：结果虽然是确定的，但开放给第三方会让任务在 `deadline` 到达的瞬间被人抢先取消，剥夺发布方宽限的余地。双方都能调用即可避免资金卡死。

**配套修复**：`acceptTask` 增加 deadline 校验，禁止接单已过期的任务（否则接单即可被立刻判交付超时）。

**代码**：`AgentTaskEscrow.REVIEW_WINDOW = 7 days` / `claimDeliveryTimeout()` / `claimReviewTimeout()`
